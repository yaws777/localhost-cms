# AGENTS.md

## Structure
- `backend/src/database/connection.js` — the entire Express API + MySQL pool + listen. `backend/src/routes/server.js` is dead commented-out code; `backend/src/services/` (`login.js`, `forgotpassword.js`) is unused. Do not add routes elsewhere.
- `frontend/src/index.js` — all routes (`/` landing `App.js`, `/Login`, nurse/*, student/*, parent/* under layout wrappers). `frontend/src/pages|components|layout|hooks|utils` per role.
- DB schema source: `cms schema (1).sql`. MySQL database `ClinicManagementSystem` required locally; no migrations, no ORM, raw `mysql2/promise` queries.
- No monorepo tooling, no tests in backend (`npm test` just errors), no lint/typecheck config, no CI.

## Doctor portal
- Role `DCTR` (`roles`), accounts are created by the nurse (`/ManageDoctorAccounts`, `POST /api/doctor-accounts`): default password `"123"`, `doctors.user_id` links the login. On first login `DoctorLayout` blocks the portal until the doctor saves a phone number (`PUT /api/doctor/phone` sets `phone_confirmed_at`); that number is the forgot-password identifier for doctors.
- Routes `/DoctorDashboard`, `/DoctorMySchedule` (not `/DoctorSchedule`, that is a nurse redirect), `/DoctorConsultations` (tabs Upcoming / On going / Past Consultation, Direct appointment, Walk-in only on the On going tab; `/DoctorAppointments` was removed and redirects here, booking approvals live in My Schedule > Booking approvals), `/DoctorPatients`, `/DoctorTemplates`, `/DoctorProfile` under `frontend/src/layout/doctorLayout.jsx`; pages in `frontend/src/pages/doctor`, shared pieces in `frontend/src/components/doctor`.
- Consultation lists are one shared screen, `components/scheduling/ConsultationLists.jsx` (`role="doctor"` in `/DoctorConsultations`, `role="nurse"` in Doctor Visit > Consultation; the nurse page no longer has the Program/Section folders, batch cards or QR scan). Past Consultation is one folder per day (`GET /api/doctor/:doctorId/appointment-days`, `doctorId` can be `all` + `?doctor_id=`), a folder opens that day's table. Doctor past rows: assessment history (`/api/doctor/patients/:studentId/record`) and **Repeat** (`RepeatModal` in `FollowUps.jsx`: direct appointment, or wait for a schedule via `PUT /api/follow-ups/:id/flag`); nurse past rows only open `AssessmentViewModal`. The sidebar dot on Consultations is today's state: green on going, yellow still to come, gray all over.
- Visit purposes (the student's "purpose of consultation") come from the `specializations` table (`migration_specializations_visit_types.sql`, run after `migration_hybrid_schedules.sql`): every specialization has one `visit_type` (several can share one, e.g. Optometrist/Ophthalmologist = Vision), so adding a specialization (`POST /api/specializations`, from the picker in Manage Doctor Accounts) adds a purpose. `General Check Up` belongs to General Physician and every doctor can take it; `Follow-up` / `Referral` are system types. **`Other` was removed** (old `Other: ...` rows still display through `visitLabel`; the CHECK constraints on visit_type were dropped, the server validates against the table). Backend registry: `SPECIALIZATIONS` / `VISIT_PURPOSES` / `DOCTOR_VISIT_TYPES` are arrays refilled by `loadSpecializations()`; frontend: `hooks/useSpecializations.js` (`visitTypes`), never a hardcoded list.
- Scheduling types: direct appointment (`POST /api/doctor-appointments/direct`, custom time block), open time block (`doctor_schedules`, `auto_confirm` decides whether bookings need approval), walk-in. Cancel / decline / reschedule require a reason and every change is written to `doctor_appointment_logs` (`logAppointment`). `doctor_unavailable_dates` blocks booking.
- DB changes live in `migration_doctor_role_portal.sql` (run after `migration_doctor_schedule_booking.sql`, idempotent, use `--default-character-set=utf8mb4`).

## Consultation scheduling (waiting list + schedule types)
- `migration_consultation_scheduling.sql` (run after `migration_doctor_role_portal.sql`, idempotent): appointment status `Pending Approval` is now **`Waiting for Approval`** everywhere; `doctor_schedules.schedule_type` (`Appointment | Open Slot | Walk-in`, + `announcement`, `extended_minutes`); `consultation_requests` (+ `_logs`); `doctors.services_offered` / `services_notes`; assessment metadata (`chief_complaint`, `visit_type`, `documented_by_role/name`).
- `migration_schedule_modes_followups_chat.sql` (run after the one above, idempotent): `doctor_schedules.allow_appointment | allow_open_booking | allow_walk_in` (the real definition of a schedule; `schedule_type` is only the label derived by `scheduleTypeFromModes`: `Appointment | Open Slot | Hybrid | Walk-in`) and `doctor_assessments.follow_up_closed(_reason)`. Backend helpers `hasSlots(s)` (appointment or open booking) / `scheduleLiveState(s)`; frontend `hasAppointment/hasOpenBooking/hasWalkIn/hasSlots` in `utils/scheduling.js`. Do not branch on `schedule_type === 'Walk-in'` etc.; use the switches.
- `migration_hybrid_schedules.sql` (after the one above, idempotent): no schedule type is chosen any more. `validateScheduleInput` forces `allow_appointment = allow_open_booking = 1` (`schedule_type` is always `Hybrid`); the only per-schedule switch is `allow_walk_in` (`POST /api/doctor-visits/walk-in` refuses when every running session has it off; appointments still come first, the response carries a `queue_note`). Open-slot bookings need approval unless `auto_confirm`. Sessions and single appointments can be extended (`PUT /api/doctor-schedules/:id/extend`, `PUT /api/doctor-visits/extend/:id`).
- How a student was scheduled is categorized from `doctor_appointments.booking_source` (frontend `SCHEDULING_WAYS` / `wayOf` in `utils/scheduling.js`, `sourceLabel` in `visitPurpose.js`): `Nurse|Doctor` = by appointment, `Student` = by open time slot, `Walk-in` = walk-in. `GET /api/schedule-calendar` sessions carry `by_appointment | by_open_slot | by_walk_in` counts.
- Schedule form has no Repeats (a new schedule is one date) and one text, **Notes for Students** (`notes`; `announcement` is kept equal to it by `validateScheduleInput`). Session cards (calendar) have Participants (`GET /api/doctor-schedules/:id/participants?date=`) and, while in session and `allow_walk_in`, Add walk-in (the hub no longer has a Walk-in button; the nurse Doctor Visit header has no action buttons).
- Schedule CRUD: `POST/GET/PUT/DELETE /api/doctor-schedules`. **Ongoing** (`is_ongoing`: a session is running now, or a weekly series already started) cannot be deleted, close it first; a session in progress (`in_session_now`) also freezes its dates/hours (extend instead). Delete is also refused when the schedule has any booking.
- One active appointment (`Scheduled | Waiting for Approval`) per student per schedule and day: `assertAppointmentFits` refuses booking, appointing (`/appoint`, `/auto-appoint`) and follow-up-into-session until the first one is cancelled; `buildSlots` marks the day's slots unavailable for that student (moving one's own booking passes `exclude_appointment_id` to `/slots`).
- Purpose of the consultation must match everywhere: the student must pick one when booking (`POST /api/student/doctor-bookings` requires `visit_type`, and a block with a fixed purpose only takes that purpose); staff appointing (`/appoint`) take it from the request or must state it, and it has to match both the request and the session (`linkRequestToAppointment` enforces the request match).
- Consultation request flow (statuses in `consultation_requests.status`): student asks → `Waiting for Approval` → nurse/doctor approve (`Waiting List`) or deny with a reason (`Denied`) → `POST /api/consultation-requests/notify` is the only notice there is: it asks the selected students to reconfirm for a session (always `Awaiting Reconfirmation`, student answers `Reconfirmed`/`Withdrawn`; no remind function exists any more; the session card's Reconfirm button opens the waiting list with the session picked, "Appoint from waiting list" opens the Reconfirmed students, and `auto-appoint` takes `request_ids` for the selected ones). Approving a request tells the student to stay active for the nurse's reconfirmation → `POST /api/doctor-schedules/:id/appoint` (any request still `Waiting List | Awaiting Reconfirmation | Reconfirmed` can be appointed or moved into any session that has slots) or `/auto-appoint` (reconfirmed only) (`Appointed`), student booking (`Booked`), walk-in (`Fulfilled`). Cancelled/declined appointments return the request to `Waiting List`.
- Follow-ups (the hub tab is called **Repeats**; assessment fields say "Repeat") are always set per student: `GET /api/follow-ups` lists assessments with `follow_up_needed` (`needs_time | scheduled | done | dismissed`), `POST /api/doctor-visits/:appointment_id/follow-up` appoints one (custom time, or `schedule_id` for a slot in a session; one open follow-up per assessment), `PUT /api/follow-ups/:appointment_id/dismiss` takes it off the list. A repeat is the next follow-up assessed and flagged again. Follow-up/Referral cannot go in `POST /api/mass-schedules`.
- Nurse ↔ doctor chat reuses `messages` (+ `/api/messages/send|history|read`); `GET /api/staff-chat/contacts/:userId` and `/api/staff-chat/unread/:userId` list the counterpart staff. UI: `components/scheduling/StaffChat.jsx` (hub tab "Chat", doctor page `/DoctorChat`); the nurse Messages page also lists doctors.
- Doctor coverage: a doctor can take `allowed_visit_types` (General Check Up + what the specialization adds) and chooses `covered_visit_types` from them in My Profile (`PUT /api/doctor/:id/services`, saved in `doctors.services_offered`, NULL = everything allowed; `services_notes` is no longer used). Every doctor payload (`/api/doctors`, `/api/doctor-accounts`, `/api/get-doctor`) and every schedule / calendar session / student occurrence carries them. `visitRefusal(doctor, visitType)` (backend) / `visitRefusal` in `frontend/src/utils/scheduling.js` enforce it; UI lists only eligible doctors, the nurse sees `Covers: ...` when appointing, the student sees it on each open schedule, and a doctor only sees consultation requests whose purpose they cover (`GET /api/consultation-requests?doctor_id=`).
- Past / ongoing / upcoming rules: a session or appointment is `upcoming` (not started: edit, delete, appoint, reschedule, cancel), `ongoing` (happening now: appoint into what is left, **extend** - extend is refused for upcoming sessions/appointments and the schedule's dates/hours are locked) or `past` (closed: no booking, appointing, walk-in, editing, rescheduling or cancelling; `schedule-calendar` returns `state` for sessions and appointments). Walk-ins need a session running right now that allows them. Unanswered `Waiting for Approval` bookings are declined automatically once their slot starts (`expireUnansweredBookings`, every 5 minutes). Doctor appointment lists use `scope=requests|upcoming|ongoing|past` (disjoint).
- Schedule form is one component (`components/scheduling/ScheduleFormModal.jsx`) used by the Schedules tab and the calendar day panel (add / edit / delete a schedule, appoint, reschedule / cancel an appointment). The nurse and the doctor mount the same `SchedulingHub` (Direct appointment and Walk-in buttons live there); there is no Add Doctor on the Doctor Visit page - doctors are created in Manage Doctor Accounts.
- One screen for both roles: `frontend/src/components/scheduling/SchedulingHub.jsx` (tabs Calendar | Schedules | Waiting list | Repeats | Booking approvals | Assistant | Chat). Nurse mounts it in `DoctorVisit` (`?section=availability|requests|waiting|followups|chat`), the doctor in `/DoctorMySchedule` (`?tab=`); the doctor passes `fixedDoctorId`. Shared data: `GET /api/schedule-calendar`, `GET /api/scheduling-assistant` (demand, alerts, suggested sessions), `GET /api/doctor-schedules`. Students use `bookCheckup.jsx` (requests, reconfirm, announcements from `GET /api/doctor-schedules/announcements`).

## Backend (`backend/`, CommonJS)
- Run: `cd backend && npm start` → `nodemon src/database/connection.js`, serves on port **3001** (`app.listen(3001)` at file end).
- Needs `backend/.env` (gitignored-ish, exists locally): `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `IPROG_API_TOKEN`, `IPROG_SMS_ENDPOINT`, `DEFAULT_COUNTRY_CODE`. Never commit real values; code has hardcoded MySQL creds (`root` / `Yahweh0512` @ `localhost`) — keep local-only.
- Single ~9000-line file: search by `app.get|app.post|app.put|app.delete` section headers (login, profile, requirements, clinic-visits, incident-reports, inventory, notifications, push-subscriptions, messages). Add new endpoints inline there.
- Uploads: multer `diskStorage` to `backend/uploads/`, served at `/uploads`; file URLs built as `http://localhost:3001/uploads/...`.
- SMS: Twilio client initialized but visit/incident alerts send via iProg (`sendIprogSms`, form-urlencoded, PH numbers normalized to `09XXXXXXXXX`). Web push via `web-push` + `push_subscriptions` table; note codebase mixes `webpush.sendNotification` (correct) and `webpush.sendPushNotification` (broken) — use `sendNotification`.
- Passwords are bcrypt hashes in `users.password_hash` (`backend/src/utils/security.js`: `hashPassword` / `verifyPassword`; login still upgrades any leftover plaintext row). Default password is `"123"` (login returns `isDefaultPassword` from the typed password). Always `await hashPassword()` before writing `password_hash`.
- `messages.content` is AES-256-GCM encrypted (`enc:v1:` prefix) via `encryptText` on insert and `decryptMessageRows` on every read. Key is `MESSAGE_ENCRYPTION_KEY` in untracked `backend/.env.local` (losing it makes stored messages unreadable; back it up). `notifyUsers` stores a generic text for `MESSAGE` notifications. One-time migration: `node backend/scripts/encryptExistingData.js` (idempotent).

## Frontend (`frontend/`, CRA + React 18 + react-router-dom v6)
- Run: `cd frontend && npm start` (CRA dev server, port 3000). `npm run dev` / `vite` scripts exist but repo is CRA (`react-scripts`, `src/index.js`, `App.js`); prefer `npm start` and `npm run build` / `npm test` (react-scripts).
- API base is hardcoded `http://localhost:3001` per-fetch (only `studentDashboard.jsx` honors `VITE_API_BASE_URL`). Keep hardcoded pattern; `backend/package.json` `"proxy"` field is ineffective for this setup. Both servers must run.
- Auth state in `localStorage` (`userId`, role ids); role routing by `role_id`/`role` from `/api/login`.
- Styling: per-page CSS in `src/styles/` + Tailwind v4 (`@tailwindcss/vite`) + `lucide-react` icons.
