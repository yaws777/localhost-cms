# AGENTS.md

## Structure
- `backend/src/database/connection.js` — the entire Express API + MySQL pool + listen. `backend/src/routes/server.js` is dead commented-out code; `backend/src/services/` (`login.js`, `forgotpassword.js`) is unused. Do not add routes elsewhere.
- `frontend/src/index.js` — all routes (`/` landing `App.js`, `/Login`, nurse/*, student/*, parent/* under layout wrappers). `frontend/src/pages|components|layout|hooks|utils` per role.
- DB schema source: `cms schema (1).sql`. MySQL database `ClinicManagementSystem` required locally; no migrations, no ORM, raw `mysql2/promise` queries.
- No monorepo tooling, no tests in backend (`npm test` just errors), no lint/typecheck config, no CI.

## Doctor portal
- Role `DCTR` (`roles`), accounts are created by the nurse (`/ManageDoctorAccounts`, `POST /api/doctor-accounts`): default password `"123"`, `doctors.user_id` links the login. On first login `DoctorLayout` blocks the portal until the doctor saves a phone number (`PUT /api/doctor/phone` sets `phone_confirmed_at`); that number is the forgot-password identifier for doctors.
- Routes `/DoctorDashboard`, `/DoctorMySchedule` (not `/DoctorSchedule`, that is a nurse redirect), `/DoctorCheckup` (page `doctorCheckup.jsx`; `/DoctorConsultations` redirects here; tabs Upcoming / On going / Past Check-up, Direct appointment, Walk-in only on the On going tab; `/DoctorAppointments` was removed and redirects here, booking approvals live in My Schedule > Booking approvals), `/DoctorPatients`, `/DoctorTemplates`, `/DoctorProfile` under `frontend/src/layout/doctorLayout.jsx`; pages in `frontend/src/pages/doctor`, shared pieces in `frontend/src/components/doctor`.
- Consultation lists are one shared screen, `components/scheduling/ConsultationLists.jsx` (`role="doctor"` in `/DoctorCheckup`, `role="nurse"` in Doctor Visit > Check-up; the nurse page no longer has the Program/Section folders, batch cards or QR scan). Upcoming and Past Check-up show one **container per session day** first (`GET /api/doctor/:doctorId/appointment-groups`, a schedule on a date, or the direct appointments of a doctor on a date; `doctorId` can be `all` + `?doctor_id=`); opening one lists its participants (`/appointments?schedule_id=<id|none>&doctor_id=&from=&to=`). `appointment-days` stays unused. On going: each queue number has **Time in** (manual) or **Scan QR** (`AttendanceScanModal`, jsQR, QR = student ID) which marks it `Present`; **Document** appears only after that. **Void** replaces Skip (same endpoint `/queue/skip`; voiding the number in session calls the next); **Back to number** on a void row (`PUT /api/doctor-visits/:id/queue/restore`, doctor, session running) puts it in session again and the number in session waits again. The Walk-in button sits beside Call next in `QueuePanel` (`onWalkIn`), not in the page header. UI says "In session" for queue state `Serving`. Doctor Listings tab has no "To accept" list (accepted / seen only) and the Schedules tab has no Close schedule (nurse only). Doctor past rows: assessment history (`/api/doctor/patients/:studentId/record`) and **Repeat** (`RepeatModal` in `FollowUps.jsx`: direct appointment, or wait for a schedule via `PUT /api/follow-ups/:id/flag`); nurse past rows only open `AssessmentViewModal`. The sidebar dot on Check-ups is today's state: green on going, yellow still to come, gray all over.
- Visit purposes (the student's "purpose of consultation") come from the `specializations` table (`migration_specializations_visit_types.sql`, run after `migration_hybrid_schedules.sql`): every specialization has one `visit_type` (several can share one, e.g. Optometrist/Ophthalmologist = Vision), so adding a specialization (`POST /api/specializations`, from the picker in Manage Doctor Accounts) adds a purpose. `General Check Up` belongs to General Physician and every doctor can take it; `Follow-up` / `Referral` are system types. **`Other` was removed** (old `Other: ...` rows still display through `visitLabel`; the CHECK constraints on visit_type were dropped, the server validates against the table). Backend registry: `SPECIALIZATIONS` / `VISIT_PURPOSES` / `DOCTOR_VISIT_TYPES` are arrays refilled by `loadSpecializations()`; frontend: `hooks/useSpecializations.js` (`visitTypes`), never a hardcoded list.
- **Check-up service** (UI name; was "Consultation service" / "Consultation offered") = the old waiting-list "category" = a visit type (API/DB/file names `categories`, `visit_type`, `/api/consultations-offered`, `ConsultationsOffered.jsx`, `migration_consultations_offered.sql` are unchanged). `migration_consultations_offered.sql` (run after `migration_specializations_visit_types.sql`, idempotent) makes `specializations` unique on `(name, visit_type)`, so a specialization can offer several consultations and a consultation can belong to several specializations. Manage Doctor Accounts has a "Check-up Services" card (`components/scheduling/ConsultationsOffered.jsx`, `GET|POST /api/consultations-offered`): pick from the list, a suggestion, or **Other** + specify; tick the specializations it belongs to (additive, new specialization can be typed); assign doctors. Only doctors whose specialization is linked can be assigned (400 otherwise); assignment is written to `doctors.services_offered` (a doctor keeps at least one consultation; unassigning is refused while the doctor has upcoming schedules of it). The waiting list lists only sessions of doctors assigned to the chosen consultation (Dental = dentists only). `useSpecializations` also exposes `specializationNames` (deduped) - never map `specializations` rows into a picker.
- **UI naming: "Consultation(s)" is "Check-up(s)"** in all user-visible text (student, doctor and nurse scheduling screens, notifications, API error messages): "Check-up Services", "Upcoming / On going / Past Check-up", "Check-ups" in the doctor sidebar. Code names stay: API paths, DB tables/columns, CSS classes, notification types (`CONSULTATION_*`), components (`ConsultationLists`, `ConsultationModal`, `ConsultationsOffered`). Renamed: `pages/doctor/doctorCheckup.jsx` (route `/DoctorCheckup`). Not renamed on purpose: the nurse clinic-visit log (`VisitLogConsultation`, reports, landing text), which is a different thing.
- Scheduling types: direct appointment (`POST /api/doctor-appointments/direct`, custom time block), open time block (`doctor_schedules`, `auto_confirm` decides whether bookings need approval), walk-in. Cancel / decline / reschedule require a reason and every change is written to `doctor_appointment_logs` (`logAppointment`). `doctor_unavailable_dates` blocks booking.
- DB changes live in `migration_doctor_role_portal.sql` (run after `migration_doctor_schedule_booking.sql`, idempotent, use `--default-character-set=utf8mb4`).

## Listing per schedule (current flow, `migration_schedule_listing.sql`)
Run `migration_schedule_listing.sql` after `migration_consultation_services.sql` (idempotent; the backend also adds the columns on start, `ensureScheduleListingColumns`). **It supersedes the per-service listing and the waiting-list/appoint/reconfirm bullets below.**
1. The nurse asks a doctor for a schedule (`POST /api/schedule-requests`).
2. The doctor sets the schedule with a **listing limit** (`doctor_schedules.listing_limit`, required, 1 to 500, in `ScheduleFormModal`, which no longer asks for minutes per patient / patients at once; the limit IS the session capacity, `queueCapacity` returns it; cannot go below the accepted count; NULL on old rows = old slot grid).
3. The nurse **opens the listing** of that schedule (`PUT /api/doctor-schedules/:id/listing`, nurse only, `doctor_schedules.listing_open`, closed by default; Schedules tab door icon or the Listings tab). Helpers: `scheduleListingOf` / `scheduleListingCounts` (accepted = Listed-lane numbers of that session day, pending = `Waiting for Approval` asks); `GET /api/doctor-schedules` carries `listing_date / listing_open / listing_limit / accepted / pending / listing_full`.
4. The student sees only open listings (`GET /api/student/:studentId/open-listings`) and asks a place in one (`POST /api/student/consultation-requests` needs `schedule_id`; request stores `listing_schedule_id` + `listing_date`; status `Waiting for Approval`, no number; refused when closed/full/over/doctor unavailable; the purpose is the schedule's, or the student's pick when the schedule is `Any`).
5. The nurse accepts (`PUT /api/consultation-requests/:id/accept`, nurse only) or declines (`PUT .../:id/deny` with a reason). **Accept = a place in the session queue**: it calls `appointIntoSchedule` (next `Listed` number of that session, order of acceptance), request -> `Appointed`, `consultation_requests.queue_no` = that session number, student and parents told (`notifyAppointed`). Refused when the listing limit is reached.
- No more waiting-list numbers (`takeQueueNo`), "Appoint next", reconfirm or service-level listing in the UI. Their endpoints (`/appoint`, `/auto-appoint`, `/notify`, `consultation_service_listing`, `PUT /api/consultations-offered/:visitType/listing`, `GET /api/consultation-requests/categories`) stay only for old rows. Hub tab `waiting` is now labelled **Listings** (`WaitingList.jsx`, one session at a time); student page `/BookCheckup` lists open listings.
- Direct appointment by the nurse/doctor (`AppointModal`, `DirectAppointmentModal`) is unchanged.

## Waiting list + session queue (current model, `migration_queue_waiting_list.sql`)
Run `migration_queue_waiting_list.sql` after `migration_specializations_visit_types.sql` (idempotent, `--default-character-set=utf8mb4`). **It supersedes the booking / approval / hybrid-slot bullets in the sections below** (student time-block booking, booking approvals, `auto_confirm`, `by_open_slot` are gone; their columns stay unused).
- **Students do not book a time.** `POST /api/student/consultation-requests` creates a **listing request** (`Waiting for Approval`, no number) for one category (`visit_type`); refused (409) when the nurse closed that service's listing or its listing limit is reached. The category must be covered by a doctor that has an account (`eligibleCategories()`, `GET /api/consultation-requests/categories`), else 409. The student gets a number only when the nurse accepts (`PUT /api/consultation-requests/:id/accept`, nurse only, refused when the limit is reached; the number is `consultation_requests.queue_no`, taken from `queue_counters` by `takeQueueNo`, so numbers follow the order of acceptance); the live position is `queue_position` / `queue_total` in `REQUEST_SELECT`. One order everywhere: `REQUEST_ORDER` (`is_priority DESC, queue_no ASC`).
- Request statuses: `Waiting for Approval -> Waiting List -> (Awaiting Reconfirmation -> Reconfirmed, optional) -> Appointed -> Fulfilled | Missed`; `Denied` (nurse/doctor decline or remove with a reason, `PUT /:id/deny`, works from `Waiting for Approval` too), `Withdrawn` (student, also while pending). `Booked` exists only for old rows. `REQUEST_VISIBLE_STATUSES` includes `Waiting for Approval`; `ACTIVE_REQUEST_STATUSES` (accepted, waiting) does not, so pending rows have no position and are not counted. A student cannot have a second open request (any of the active statuses or `Appointed`) in the same category.
- **Listing control per consultation service** (`migration_consultation_services.sql`, run after `migration_consultations_offered.sql`; the backend also creates the table on first use, `ensureServiceListingTable`): `consultation_service_listing (visit_type, listing_open, listing_limit)`; `listingOf()` returns open?, limit, `accepted` (statuses in `ACTIVE_STATUS_SQL`), `pending`, `listing_full`. The **doctors** open/close a service and set the number of listings in My Profile > "Check-up listings" (`components/scheduling/ServiceListing.jsx`, only the services the doctor covers; `PUT /api/consultations-offered/:visitType/listing` with `sender_id`, doctor only, others get 403; empty limit = no limit; `POST /api/consultations-offered` ignores listing fields). The **nurse only views** it (status chip + "x accepted of y" in the Check-up Services card of Manage Doctor Accounts, which has no listing controls). `GET /api/consultation-requests/categories` and `GET /api/consultations-offered` carry `accepted / pending / listing_open / listing_limit / listing_full` (+ `can_request`); the student's request form and `/BookCheckup` show "x of y accepted" per service. Waiting list tab "To accept" holds the pending requests (nurse: Accept / Decline; doctor: view).
- **Appointing = a place in a session queue, no time slot.** `POST /api/doctor-schedules/:id/appoint` (`student_id, date, request_id`) and "Appoint next" `POST /api/doctor-schedules/:id/auto-appoint` (`date, count | request_ids, visit_type`; takes the front of the category in `REQUEST_ORDER`) create a `doctor_appointments` row spanning the session window with `queue_lane='Listed'`, `queue_no` (next number of that schedule + day, `nextQueueNo`) and `queue_state='Waiting'`. Capacity = `queueCapacity(schedule)` (slot grid x patients per slot; the form calls them "minutes per patient" / "patients at once"). `assertQueueFits` replaces the time-slot checks; `assertAppointmentFits` / `/slots` stay for direct appointments, follow-ups, referrals and batches. Queue rows are excluded from the doctor's timed-overlap count (`queue_state IS NULL`) and cannot be rescheduled one by one (cancel + appoint again). The doctor reschedules the **whole upcoming one-date session** with `PUT /api/doctor-schedules/:id/reschedule` (`schedule_date, start_time, end_time, reason`, doctor of the schedule only, before it starts; the queue rows move with it keeping their numbers, students and parents are told; rescheduling lives inside the session's **Edit** button (`ScheduleFormModal.jsx`: for an upcoming one-date session with students queued the date/hours stay editable and ask for a reason, the form calls `PUT /api/doctor-schedules/:id/reschedule` first, then the normal PUT); there is **no separate Reschedule button** on the session card and `RescheduleSessionModal` was removed; refused when timed appointments, a clash, an unavailable day or a too-small capacity). `PUT /api/doctor-schedules/:id` still refuses timing changes while students are in the queue.
- **Queue lanes and states.** `Listed` (#1, #2 ...) is served first; `Walk-in` (W1, W2 ...) has its own numbering and is called only when no listed student waits. `queue_state`: `Waiting | Serving | Done | Void`. Doctor-only endpoints: `PUT /api/doctor-schedules/:id/queue/call-next` (refuses while the serving number is undocumented), `PUT /api/doctor-visits/:appointment_id/queue/skip` (number becomes `Void`, stays in the list, request -> `Missed`, student told). `PUT /api/doctor-visits/:appointment_id/queue/accommodate` (nurse or doctor, session running + `allow_walk_in`) creates a walk-in lane row (`parent_appointment_id` = the void row) and puts the request back to `Appointed`. `POST /api/doctor-visits/walk-in` also joins the walk-in lane of the running session. Snapshot: `GET /api/doctor-schedules/:id/queue?date=` (`buildQueueSnapshot`, `peopleAhead`). Documenting a consultation calls `finishQueueEntry` (queue `Done`, request `Fulfilled`); deleting the assessment calls `reopenQueueEntry`.
- Cron (5 min): `closeFinishedQueues` - numbers never called when the session ended are cancelled and the request returns to the waiting list keeping its place (`returnRequestToWaitingList`), the student is told; then `markExpiredAppointmentsAbsent`.
- Student: `GET /api/student/:studentId/queue-status` (`requests` = waiting list numbers + position, `appointments` = session queue numbers with `now_serving`, `ahead`, `est_wait_min`). Frontend: `hooks/useQueueStatus.js` (polls 10 s), `components/student/MyQueue.jsx`, used by `pages/student/bookCheckup.jsx` (route `/BookCheckup`, sidebar "Check-up") and the student dashboard card. Notification types `QUEUE_CALLED | QUEUE_NEAR | QUEUE_VOID` route to the dashboard.
- **Schedules are set by the doctor.** `POST /api/doctor-schedules` is doctor-only (nurse gets 403). The nurse sends `POST /api/schedule-requests` (doctor, category, preferred day/time, note; table `schedule_requests`); the doctor answers by setting a schedule with `schedule_request_id` (request -> `Scheduled`) or `PUT /api/schedule-requests/:id/decline` (reason); the nurse can `PUT .../:id/cancel`. UI: `components/scheduling/ScheduleRequests.jsx` (list + `ScheduleRequestModal`), shown in the Schedules tab and the calendar day panel.
- Staff UI: `WaitingList.jsx` (category tabs with counts, numbered table, session picker + "Appoint next N" / "Appoint selected" / optional "Ask to confirm", remove with reason, priority star; a session card's "Appoint from waiting list" opens the category of that session), `QueuePanel.jsx` (the doctor's Call next / Skip / Accommodate, nurse's Arrived / Accommodate; mounted in `ConsultationLists.jsx` On going tab per running session and in the calendar's session modal). Hub tabs: Calendar | Schedules | Waiting list | Repeats | Assistant | Chat (no Booking approvals).
- Id generation: `generateCustomIdWithRetry` (retry on `ER_DUP_ENTRY`) for ids that two requests can race for; `generateCustomId` uses the Manila date.

## Consultation scheduling (waiting list + schedule types) - older notes, partly superseded by the section above
- `migration_consultation_scheduling.sql` (run after `migration_doctor_role_portal.sql`, idempotent): appointment status `Pending Approval` is now **`Waiting for Approval`** everywhere; `doctor_schedules.schedule_type` (`Appointment | Open Slot | Walk-in`, + `announcement`, `extended_minutes`); `consultation_requests` (+ `_logs`); `doctors.services_offered` / `services_notes`; assessment metadata (`chief_complaint`, `visit_type`, `documented_by_role/name`).
- `migration_schedule_modes_followups_chat.sql` (run after the one above, idempotent): `doctor_schedules.allow_appointment | allow_open_booking | allow_walk_in` (the real definition of a schedule; `schedule_type` is only the label derived by `scheduleTypeFromModes`: `Appointment | Open Slot | Hybrid | Walk-in`) and `doctor_assessments.follow_up_closed(_reason)`. Backend helpers `hasSlots(s)` (appointment or open booking) / `scheduleLiveState(s)`; frontend `hasAppointment/hasOpenBooking/hasWalkIn/hasSlots` in `utils/scheduling.js`. Do not branch on `schedule_type === 'Walk-in'` etc.; use the switches.
- `migration_hybrid_schedules.sql` (after the one above, idempotent): no schedule type is chosen any more. `validateScheduleInput` forces `allow_appointment = allow_open_booking = 1` (`schedule_type` is always `Hybrid`); the only per-schedule switch is `allow_walk_in` (`POST /api/doctor-visits/walk-in` refuses when every running session has it off; appointments still come first, the response carries a `queue_note`). Open-slot bookings need approval unless `auto_confirm`. Sessions and single appointments can be extended (`PUT /api/doctor-schedules/:id/extend`, `PUT /api/doctor-visits/extend/:id`).
- How a student was scheduled is categorized from `doctor_appointments.booking_source` (frontend `SCHEDULING_WAYS` / `wayOf` in `utils/scheduling.js`, `sourceLabel` in `visitPurpose.js`): `Nurse|Doctor` = by appointment, `Student` = by open time slot, `Walk-in` = walk-in. `GET /api/schedule-calendar` sessions carry `by_appointment | by_open_slot | by_walk_in` counts.
- Schedule form has no Repeats (a new schedule is one date) and one text, **Notes for Students** (`notes`; `announcement` is kept equal to it by `validateScheduleInput`). Session cards (calendar) have Participants (`GET /api/doctor-schedules/:id/participants?date=`) and, while in session and `allow_walk_in`, Add walk-in (the hub no longer has a Walk-in button; the nurse Doctor Visit header has no action buttons).
- Schedule CRUD: `POST/GET/PUT/DELETE /api/doctor-schedules`. **Ongoing** (`is_ongoing`: a session is running now, or a weekly series already started) cannot be deleted, close it first; a session in progress (`in_session_now`) also freezes its dates/hours (extend instead). Delete is also refused when the schedule has any booking.
- One active appointment (`Scheduled | Waiting for Approval`) per student per schedule and day: `assertAppointmentFits` refuses booking, appointing (`/appoint`, `/auto-appoint`) and follow-up-into-session until the first one is cancelled; `buildSlots` marks the day's slots unavailable for that student (moving one's own booking passes `exclude_appointment_id` to `/slots`).
- Purpose of the consultation must match everywhere: the student must pick one when booking (`POST /api/student/doctor-bookings` requires `visit_type`, and a block with a fixed purpose only takes that purpose); staff appointing (`/appoint`) take it from the request or must state it, and it has to match both the request and the session (`linkRequestToAppointment` enforces the request match).
- Consultation request flow (statuses in `consultation_requests.status`): student asks → `Waiting for Approval` → nurse/doctor approve (`Waiting List`) or deny with a reason (`Denied`) → `POST /api/consultation-requests/notify` is the only notice there is: it asks the selected students to reconfirm for a session (always `Awaiting Reconfirmation`, student answers `Reconfirmed`/`Withdrawn`; no remind function exists any more; the session card's Reconfirm button opens the waiting list with the session picked, "Appoint from waiting list" opens the Reconfirmed students, and `auto-appoint` takes `request_ids` for the selected ones). Approving a request tells the student to stay active for the nurse's reconfirmation → `POST /api/doctor-schedules/:id/appoint` (any request still `Waiting List | Awaiting Reconfirmation | Reconfirmed` can be appointed or moved into any session that has slots) or `/auto-appoint` (reconfirmed only) (`Appointed`), student booking (`Booked`), walk-in (`Fulfilled`). Cancelled/declined appointments return the request to `Waiting List`.
- Follow-ups (the hub tab is called **Repeats**; assessment fields say "Repeat") are always set per student: `GET /api/follow-ups` lists assessments with `follow_up_needed` (`needs_time | scheduled | done | dismissed`), `POST /api/doctor-visits/:appointment_id/follow-up` appoints one (custom time, or `schedule_id` for a slot in a session; one open follow-up per assessment), `PUT /api/follow-ups/:appointment_id/dismiss` takes it off the list. A repeat is the next follow-up assessed and flagged again. Follow-up/Referral cannot go in `POST /api/mass-schedules`.
- Nurse ↔ doctor chat reuses `messages` (+ `/api/messages/send|history|read`); `GET /api/staff-chat/contacts/:userId` and `/api/staff-chat/unread/:userId` list the counterpart staff. UI: `components/scheduling/StaffChat.jsx` (hub tab "Chat", doctor page `/DoctorChat`); the nurse Messages page also lists doctors.
- Doctor coverage: a doctor can take `allowed_visit_types` (General Check Up + what the specialization adds) and chooses `covered_visit_types` from them in My Profile (`PUT /api/doctor/:id/services`, saved in `doctors.services_offered`, NULL = everything allowed; `services_notes` is no longer used). Every doctor payload (`/api/doctors`, `/api/doctor-accounts`, `/api/get-doctor`) and every schedule / calendar session / student occurrence carries them. `visitRefusal(doctor, visitType)` (backend) / `visitRefusal` in `frontend/src/utils/scheduling.js` enforce it; UI lists only eligible doctors, the nurse sees `Covers: ...` when appointing, the student sees it on each open schedule, and a doctor only sees consultation requests whose purpose they cover (`GET /api/consultation-requests?doctor_id=`).
- Past / ongoing / upcoming rules: a session or appointment is `upcoming` (not started: edit, delete, appoint, reschedule, cancel), `ongoing` (happening now: appoint into what is left, **extend** - extend is refused for upcoming sessions/appointments and the schedule's dates/hours are locked) or `past` (closed: no booking, appointing, walk-in, editing, rescheduling or cancelling; `schedule-calendar` returns `state` for sessions and appointments). Walk-ins need a session running right now that allows them. Unanswered `Waiting for Approval` bookings are declined automatically once their slot starts (`expireUnansweredBookings`, every 5 minutes). Doctor appointment lists use `scope=requests|upcoming|ongoing|past` (disjoint).
- Schedule form is one component (`components/scheduling/ScheduleFormModal.jsx`) used by the Schedules tab and the calendar day panel (add / edit / delete a schedule, appoint, reschedule / cancel an appointment). The nurse and the doctor mount the same `SchedulingHub` (Direct appointment and Walk-in buttons live there); there is no Add Doctor on the Doctor Visit page - doctors are created in Manage Doctor Accounts.
- One screen for both roles: `frontend/src/components/scheduling/SchedulingHub.jsx` (tabs Calendar | Schedules | Waiting list | Repeats | Booking approvals | Assistant | Chat). Nurse mounts it in `DoctorVisit` (`?section=availability|requests|waiting|followups|chat`), the doctor in `/DoctorMySchedule` (`?tab=`); the doctor passes `fixedDoctorId`. Shared data: `GET /api/schedule-calendar`, `GET /api/scheduling-assistant` (demand, alerts, suggested sessions), `GET /api/doctor-schedules`. Students use `bookCheckup.jsx` (requests, reconfirm, announcements from `GET /api/doctor-schedules/announcements`).

## Backend (`backend/`, CommonJS)
- Run: `cd backend && npm start` → `nodemon src/database/connection.js`, serves on port **3001** (`app.listen(3001)` at file end).
- Needs `backend/.env` (gitignored-ish, exists locally): `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `IPROG_API_TOKEN`, `IPROG_SMS_ENDPOINT`, `DEFAULT_COUNTRY_CODE`. Never commit real values; code has hardcoded MySQL creds (`root` / `Yahweh0512` @ `localhost`) — keep local-only.
- Single ~9000-line file: search by `app.get|app.post|app.put|app.delete` section headers (login, profile, requirements, clinic-visits, incident-reports, inventory, notifications, push-subscriptions, messages). Add new endpoints inline there.
- Uploads: multer `diskStorage` to `backend/uploads/`, served at `/uploads`; file URLs built as `http://localhost:3001/uploads/...`.
- SMS: Twilio client initialized but visit/incident alerts send via iProg (`sendIprogSms`, form-urlencoded, PH numbers normalized to `09XXXXXXXXX`). Web push via `web-push` + `push_subscriptions` table; note codebase mixes `webpush.sendNotification` (correct) and `webpush.sendPushNotification` (broken) — use `sendNotification`.
- Passwords are bcrypt hashes in `users.password_hash` (`backend/src/utils/security.js`: `hashPassword` / `verifyPassword`; login still upgrades any leftover plaintext row). Default password is `"123"` (login returns `isDefaultPassword` from the typed password). Always `await hashPassword()` before writing `password_hash`.
- `messages.content` is AES-256-GCM encrypted (`enc:v1:` prefix) via `encryptText` on insert and `decryptMessageRows` on every read. Key is `MESSAGE_ENCRYPTION_KEY` in untracked `backend/.env.local` (losing it makes stored messages unreadable; back it up). `notifyUsers` stores a generic text for `MESSAGE` notifications. One-time migration: `node backend/scripts/encryptExistingData.js` (idempotent).
