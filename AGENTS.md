## Structure
- `backend/src/database/connection.js` — the entire Express API + MySQL pool + listen. `backend/src/routes/server.js` is dead commented-out code; `backend/src/services/` (`login.js`, `forgotpassword.js`) is unused. Do not add routes elsewhere.
- `frontend/src/index.js` — all routes (`/` landing `App.js`, `/Login`, nurse/*, student/*, parent/* under layout wrappers). `frontend/src/pages|components|layout|hooks|utils` per role.
- DB schema source: `cms schema (1).sql`. MySQL database `ClinicManagementSystem` required locally; no migrations, no ORM, raw `mysql2/promise` queries.
- No monorepo tooling, no tests in backend (`npm test` just errors), no lint/typecheck config, no CI.

## Doctor portal
- Role `DCTR` (`roles`), accounts are created by the nurse (`/ManageDoctorAccounts`, `POST /api/doctor-accounts`): default password `"123"`, `doctors.user_id` links the login. On first login `DoctorLayout` blocks the portal until the doctor saves a phone number (`PUT /api/doctor/phone` sets `phone_confirmed_at`); that number is the forgot-password identifier for doctors.
- Routes `/DoctorDashboard`, `/DoctorMySchedule` (not `/DoctorSchedule`, that is a nurse redirect), `/DoctorCheckup` (page `doctorCheckup.jsx`; `/DoctorConsultations` redirects here; tabs Upcoming / On going / Past Check-up, Direct appointment, Walk-in only on the On going tab; `/DoctorAppointments` was removed and redirects here, booking approvals live in My Schedule > Booking approvals), `/DoctorPatients`, `/DoctorTemplates`, `/DoctorProfile` under `frontend/src/layout/doctorLayout.jsx`; pages in `frontend/src/pages/doctor`, shared pieces in `frontend/src/components/doctor`.
- Consultation lists are one shared screen, `components/scheduling/ConsultationLists.jsx` (`role="doctor"` in `/DoctorCheckup`, `role="nurse"` in Doctor Visit > Check-up; the nurse page no longer has the Program/Section folders, batch cards or QR scan). Upcoming and Past Check-up show one **container per session day** first (`GET /api/doctor/:doctorId/appointment-groups`, a schedule on a date, or the direct appointments of a doctor on a date; `doctorId` can be `all` + `?doctor_id=`); opening one lists its participants (`/appointments?schedule_id=<id|none>&doctor_id=&from=&to=`). `appointment-days` stays unused. On going: each queue number has **Time in** (manual) or **Scan QR** (`AttendanceScanModal`, jsQR, QR = student ID) which marks it `Present`; **Document** appears only after that. **Void** replaces Skip (same endpoint `/queue/skip`; voiding the number in session calls the next); **Back to number** on a void row (`PUT /api/doctor-visits/:id/queue/restore`, doctor, session running) puts it in session again and the number in session waits again. The Walk-in button sits beside Call next in `QueuePanel` (`onWalkIn`), not in the page header. UI says "In session" for queue state `Serving`. Doctor Listings tab has no "To accept" list (accepted / seen only) and the Schedules tab has no Close schedule (nurse only). Doctor past rows: assessment history (`/api/doctor/patients/:studentId/record`) and **Repeat** (`RepeatModal` in `FollowUps.jsx`: direct appointment, or wait for a schedule via `PUT /api/follow-ups/:id/flag`); nurse past rows only open `AssessmentViewModal`. The sidebar dot on Check-ups is today's state: green on going, yellow still to come, gray all over.
- **Queue flow on the On going tab (supersedes the Time in / Scan QR / Void / Back to number wording above).** The doctor operates the queue; the nurse only adds walk-ins and records a time in. **Call next** CALLS a number (queue state `Serving`, no time in yet = shown as "Called - time in"; with a time in = "In session"). **Time in** (nurse or doctor) exists only on the called number; there is no Time in on a waiting number and **no Scan QR** in `QueuePanel` any more. A called number that has not timed in is **Skipped** (`PUT /api/doctor-visits/:id/queue/skip` with `mode: 'skip'`: state `Void` + `doctor_appointments.queue_skipped_at`, the frontend then calls the next number) or **Voided** (`mode` omitted/`void`: state `Void`, `queue_skipped_at` NULL, final, the next number is NOT called by itself). **Call** on a skipped number = `PUT .../queue/restore` (doctor only, refused unless `queue_skipped_at` is set and while a number is in session with a time in; a called number that has not timed in is skipped automatically by this call and by Call next, `autoSkipCalledEntry`). A voided student comes back only as a **walk-in** (the Add walk-in button, nurse or doctor, `POST /api/doctor-visits/walk-in`, which links the new W number to the void row through `parent_appointment_id`, shown as "Walk-in W1"); the per-row Accommodate / Back to number buttons are gone (endpoint `/queue/accommodate` stays). `queue_skipped_at` is added on start by `ensureQueueSkippedColumn` (no .sql file). Snapshot entries carry `skipped`. Page layout (nurse `pages/nurse/doctorVisits.jsx` and doctor `pages/doctor/doctorCheckup.jsx`): `.workspace-dv` = wide main column + `components/scheduling/TodayRail.jsx` side rail from 1180px (Today counts via `hooks/useTodaySessions.js` = `GET /api/schedule-calendar`, new updates for the nurse only, doctors on duty / the doctor's own sessions; styles in `styles/scheduling/TodayRail.css`). The queue itself is one shared `QueuePanel`, so the doctor page has the same flow.
- Visit purposes (the student's "purpose of consultation") come from the `specializations` table (`migration_specializations_visit_types.sql`, run after `migration_hybrid_schedules.sql`): every specialization has one `visit_type` (several can share one, e.g. Optometrist/Ophthalmologist = Vision), so adding a specialization (`POST /api/specializations`, from the picker in Manage Doctor Accounts) adds a purpose. `General Check Up` belongs to General Physician and every doctor can take it; `Follow-up` / `Referral` are system types. **`Other` was removed** (old `Other: ...` rows still display through `visitLabel`; the CHECK constraints on visit_type were dropped, the server validates against the table). Backend registry: `SPECIALIZATIONS` / `VISIT_PURPOSES` / `DOCTOR_VISIT_TYPES` are arrays refilled by `loadSpecializations()`; frontend: `hooks/useSpecializations.js` (`visitTypes`), never a hardcoded list.
- **Check-up service** (UI name; was "Consultation service" / "Consultation offered") = the old waiting-list "category" = a visit type (API/DB/file names `categories`, `visit_type`, `/api/consultations-offered`, `ConsultationsOffered.jsx`, `migration_consultations_offered.sql` are unchanged). `migration_consultations_offered.sql` (run after `migration_specializations_visit_types.sql`, idempotent) makes `specializations` unique on `(name, visit_type)`, so a specialization can offer several consultations and a consultation can belong to several specializations. Manage Doctor Accounts has a "Check-up Services" card (`components/scheduling/ConsultationsOffered.jsx`, `GET|POST /api/consultations-offered`): pick from the list, a suggestion, or **Other** + specify; tick the specializations it belongs to (additive, new specialization can be typed); assign doctors. Only doctors whose specialization is linked can be assigned (400 otherwise); assignment is written to `doctors.services_offered` (a doctor keeps at least one consultation: one left with none falls back to General Check Up; unassigning is refused while the doctor has upcoming schedules of it; the **last doctor can be unassigned**, the service stays listed as "Not available" and cannot be used: `eligibleCategories()` leaves it out, `registerAdvance` refuses it, and schedules / appointments need a covering doctor). The waiting list lists only sessions of doctors assigned to the chosen consultation (Dental = dentists only). `useSpecializations` also exposes `specializationNames` (deduped) - never map `specializations` rows into a picker.
- **UI naming: "Consultation(s)" is "Check-up(s)"** in all user-visible text (student, doctor and nurse scheduling screens, notifications, API error messages): "Check-up Services", "Upcoming / On going / Past Check-up", "Check-ups" in the doctor sidebar. Code names stay: API paths, DB tables/columns, CSS classes, notification types (`CONSULTATION_*`), components (`ConsultationLists`, `ConsultationModal`, `ConsultationsOffered`). Renamed: `pages/doctor/doctorCheckup.jsx` (route `/DoctorCheckup`). Not renamed on purpose: the nurse clinic-visit log (`VisitLogConsultation`, reports, landing text), which is a different thing.
- Scheduling types: direct appointment (`POST /api/doctor-appointments/direct`, custom time block), open time block (`doctor_schedules`, `auto_confirm` decides whether bookings need approval), walk-in. Cancel / decline / reschedule require a reason and every change is written to `doctor_appointment_logs` (`logAppointment`). `doctor_unavailable_dates` blocks booking.

## Listing per schedule (current flow, `migration_schedule_listing.sql`)
Run `migration_schedule_listing.sql` after `migration_consultation_services.sql` (idempotent; the backend also adds the columns on start, `ensureScheduleListingColumns`). **It supersedes the per-service listing and the waiting-list/appoint/reconfirm bullets below.**
1. The nurse asks a doctor for a schedule (`POST /api/schedule-requests`).
2. The doctor sets the schedule with a **listing limit** (`doctor_schedules.listing_limit`, required, 1 to 500, in `ScheduleFormModal`, which no longer asks for minutes per patient / patients at once; the limit IS the session capacity, `queueCapacity` returns it; cannot go below the accepted count; NULL on old rows = old slot grid).
3. The nurse **opens the listing** of that schedule (`PUT /api/doctor-schedules/:id/listing`, nurse only, `doctor_schedules.listing_open`, closed by default; Schedules tab door icon or the Listings tab). Helpers: `scheduleListingOf` / `scheduleListingCounts` (accepted = Listed-lane numbers of that session day, pending = `Waiting for Approval` asks); `GET /api/doctor-schedules` carries `listing_date / listing_open / listing_limit / accepted / pending / listing_full`.
4. The student sees only open listings (`GET /api/student/:studentId/open-listings`) and asks a place in one (`POST /api/student/consultation-requests` needs `schedule_id`; request stores `listing_schedule_id` + `listing_date`; status `Waiting for Approval`, no number; refused when closed/full/over/doctor unavailable; the purpose is the schedule's, or the student's pick when the schedule is `Any`).
5. The nurse accepts (`PUT /api/consultation-requests/:id/accept`, nurse only) or declines (`PUT .../:id/deny` with a reason). **Accept = a place in the session queue**: it calls `appointIntoSchedule` (next `Listed` number of that session, order of acceptance), request -> `Appointed`, `consultation_requests.queue_no` = that session number, student and parents told (`notifyAppointed`). Refused when the listing limit is reached.
- No more waiting-list numbers (`takeQueueNo`), "Appoint next", reconfirm or service-level listing in the UI. Their endpoints (`/appoint`, `/auto-appoint`, `/notify`, `consultation_service_listing`, `PUT /api/consultations-offered/:visitType/listing`, `GET /api/consultation-requests/categories`) stay only for old rows. Hub tab `waiting` is now labelled **Listings** (`WaitingList.jsx`, one session at a time); student page `/BookCheckup` lists open listings.
- Direct appointment by the nurse/doctor (`AppointModal`, `DirectAppointmentModal`) is unchanged.
- **Doctor cannot add a free schedule.** No "Add schedule" in the doctor Calendar / Schedules / Assistant. A doctor sets a schedule only by answering a nurse request (Set schedule, `schedule_request_id`); `POST /api/doctor-schedules` returns 403 without one. The Listings tab has no Advance Listing switch for the doctor (session listings only).
- **Templates and the standard form.** No "in use" star / default any more (`is_default` column is no longer set). The schedule form has no template field any more: the doctor picks the template (optional, one at a time) in a dropdown inside `ConsultationModal` when documenting a check-up (active templates of the doctor that fit the check-up purpose; when editing, the one saved with it is selected). `doctor_schedules.template_id` stays unused. The **standard check-up form** is editable per doctor: a pinned row in Templates (`doctorTemplates.jsx`), `GET|PUT /api/doctor/:id/standard-form` (table `doctor_standard_forms`, created on first use; labels, hints, required for chief complaint / treatment plan, prescription part on / off; findings and diagnosis stay required because the server needs them; `utils/standardForm.js` holds the defaults, `mergeStandardForm` the server ones). `ConsultationModal` applies it. The standard form is a per-doctor ordered list of fields (`{ fields, prescription_enabled }`, `utils/standardForm.js`, `mergeStandardForm` on the server; the first version with `enabled` / `custom_fields` is migrated on read) edited with the same `components/doctor/FieldBuilder.jsx` as a template: every field can change type / options / hint / required, move, be removed or added. Four keys are core and saved in the assessment columns (`chief_complaint`, `clinical_findings`, `diagnosis`, `treatment_recommendations`; a checklist is saved as "a, b"; a removed core question is saved empty and the server only requires the core fields still in the doctor's form); every other field has a key `s1, s2 ...` given by the server and its answer goes to `doctor_assessments.template_responses` beside the template's. The "Appoint the repeat now" box in `ConsultationModal` is nurse-only.
- **Repeats: the doctor flags, the nurse schedules.** The doctor marks a repeat while documenting the assessment (or `RepeatModal` on a past row = flag only, `PUT /api/follow-ups/:id/flag`); the student shows in the Repeats tab. The doctor's Repeats tab has no Appoint, and `POST /api/doctor-visits/:id/follow-up` returns 403 for a doctor. The nurse's schedule request (`ScheduleRequestModal`) lists the doctor's repeats that wait for a schedule (`state=needs_time`, same check-up service); the picked ones are sent as `repeats: [{appointment_id, student_id}]` and stored in `schedule_requests.repeat_ids / repeat_count` (columns added by `ensureAdvanceListing`). When the doctor answers the request, `placeRepeatEntries` puts them in the session FIRST (visit_type `Follow-up`, parent = the assessment visit, up to the listing limit; the rest stay in the Repeats list), then `placeAdvanceEntries` fills the places left (repeats have priority over the advance listing and count toward the limit). **No double request**: `usePendingScheduleRequests` (in `ScheduleRequests.jsx`) reads the pending requests; the advance listing's Request schedule button is disabled for a service that has one, the modal disables that service and any repeat already inside a pending request, and `POST /api/schedule-requests` refuses both (409). The Session Listing Queue tab shows repeats placed in a session as `Repeat list` (`participants[].is_repeat`: `Follow-up` with a `parent_appointment_id`).
- **Confirm the end of a session / screening** (`migration_session_end_confirmation.sql`; the backend also creates the table/columns on start). When the end time passes, a session (or screening) is **not** past yet: it stays on going with `awaiting_end`, and the nurse or doctor gets `SessionEndPrompt` (`components/scheduling/SessionEndPrompt.jsx`): **Confirm end time** (moves to Past Check-up / Past Screening) or **Extend end time** (minutes counted from the end time, or from now when that passed; same date only, max 23:59; then the question comes again at the new end). **Ask me later** keeps a button on the session card. The date passing ends it by itself (cron `runPastVisitJobs`, 5 min). Check-up: `session_end_confirmations (schedule_id, session_date)`, `PUT /api/doctor-schedules/:id/end-session` (after the end time only) and the existing `PUT .../extend` (now also allowed past the end time while unconfirmed). Backend helpers: `scheduleLiveState(s, endConfirmed)` / `liveStateOf(conn, s)` (awaiting counts as `in_session_now`, so call-next / walk-in / accommodate still work), `sessionPhaseOf`, `AWAITING_END_SQL` (used by `appointmentFilter` ongoing/past, `closeFinishedQueues`, `markExpiredAppointmentsAbsent`); `GET /api/schedule-calendar` sessions carry `awaiting_end / end_confirmed`. Screening: `screening_schedules.end_confirmed_at / extended_minutes / original_end_time`, `PUT /api/screenings/:id/confirm-end` and `/extend`, `screeningPhaseOf`, tab CTE past = cancelled, confirmed or date passed; make-up needs the end confirmed. UI: prompt in `ConsultationLists` (any tab, polls 30 s), `ScheduleCalendar` session card (Confirm end time button) and `healthScreening.jsx` (polls the calendar list).
- **Student dashboard queue**: `GET /api/student/:id/queue-status` appointments carry `session_over` (end confirmed or date passed), `documented`, `in_session` (true while awaiting the end). The dashboard hides `session_over` numbers; a number whose check-up is documented shows a **Done** pill (`MyQueue`). `live-screenings` drops ended screenings (confirmed or date passed); one past its end time but unconfirmed stays as ongoing.
- **Repeats > "Put in a schedule" has no time slot**: `FollowUps.jsx` lists the doctor's upcoming schedules of the same check-up service (`visit_type` equal or `Any`; full ones disabled) and posts `{ schedule_id, date: next_date }` without `start_time` to `POST /api/doctor-visits/:id/follow-up`, which calls `appointIntoSchedule` (queue number, `visit_type = 'Follow-up'`, `parent_appointment_id` set). With `start_time` the endpoint still makes a timed direct appointment. Only sessions that have not started are offered (same check-up service or `Any`, date and start time still to come; on going, awaiting-end and past ones are hidden, and the endpoint refuses them); a session where the student already holds a number is disabled (`assertQueueFits` refuses a second place anyway).
- Student dashboard polls every 10 s (`LIVE_REFRESH_MS`, silent refresh, also on tab focus): `GET /api/student/dashboard/live-screenings/:studentId` (screenings the student is a participant of, with `phase` and own attendance), doctor appointments, and `useQueueStatus`. Health Screening ongoing rows have a manual **Time in** button (same `scan-qr` endpoint as the QR scan).

- **Advance listing** (`migration_advance_listing.sql`, run after `migration_school_years.sql`, idempotent; the backend also creates it on start, `ensureAdvanceListing`). Needs no schedule. Tables `advance_listing_settings` (one row: `is_open`, `closes_at`), `advance_listing_services (visit_type, listing_limit)`, `advance_listing_entries` (student, service, reason, `advance_no` per service shown as `A1`, status `Waiting | Scheduled | Withdrawn | Removed`, `schedule_id / session_date / appointment_id` once placed), `schedule_requests.for_advance / advance_count`. Nurse: Scheduling > Listings > **Advance listing** (`AdvanceListing.jsx`; the Listings tab now has an Advance listing / Session listings switch in `SchedulingHub`, doctor sees it read only): open with services + a limit each + "close automatically on" or until closed (`GET|PUT /api/advance-listing`, nurse only), students listed per check-up service, **Request schedule** per service sends a normal schedule request with `advance_listing: true` (`for_advance = 1`), remove with reason (`PUT /api/advance-listing/entries/:id/remove`). Student: `/BookCheckup` > Advance listing (`POST /api/student/advance-listing`, `PUT .../:id/withdraw`); one active entry at a time (`advanceEntryOf`, `ADVANCE_ACTIVE_SQL`), the form is disabled while in it, and `GET /api/student/:id/open-listings` returns `[]` + `in_advance` for them. When the doctor answers an advance request (`POST /api/doctor-schedules` with `schedule_request_id`), `placeAdvanceEntries` puts the waiting students of that service into the session in advance order (queue `#1..#n`, up to the listing limit), then **auto-opens the schedule listing** for the places left; those who ask later are accepted after them. `scheduleListingOf` / `GET /api/doctor-schedules` / `open-listings` carry `advance / regular / places_left`; `GET /api/schedule-calendar` sessions carry `by_advance / listing_open / listing_limit`. Shown on the student dashboard calendar + queue card, the doctor Schedules row, Listings session bar and calendar session card.
- **Advance listing = batches, cut off, no show** (columns added by `ensureAdvanceListing`: `advance_listing_services.moved_at`, `advance_listing_entries.cutoff_schedule_id / cutoff_date / moved_to_entry_id`, `advance_listings.completed_at`; not in the .sql file). A listing is one **batch**. A service moves to the Session Listing when it gets a schedule (`moved_at`, `syncAdvanceListing`) and is **Done** when its session is over and nobody waits (`advanceServiceDone`, service status `Open | Closed | Scheduled | Done`). When registration is closed and every service is Done the batch is complete (`completed_at`, unanswered `Pending` requests are denied); only then `PUT /api/advance-listing` starts a new batch (title required). While a batch runs but registration is closed, the same call just reopens it. `advanceStateOf` returns `batch_running / batch_complete / batch_done_services / cutoff_total` and per service `cutoff / in_session / done`; the history (`/api/advance-listing/history`) lists complete batches. `syncAdvanceListing` also runs in `runPastVisitJobs` (5 min).
- **Cut off**: `placeAdvanceEntries` places waiting students in order up to the schedule's listing limit; the rest become `Cutoff` (remember `cutoff_schedule_id`, student told) and leave the batch. Cancelling that schedule (`DELETE /api/doctor-schedules/:id`) puts the `Scheduled` and the `Cutoff` students back to `Waiting` (list whole again, service `moved_at` cleared, registration reopened). Nurse moves cut off students to the open batch with `PUT /api/advance-listing/cutoff/move` (`entry_ids`; old entry -> `Moved`, new `Waiting` entry with the next advance number, stops at the service limit). `GET /api/advance-listing/entries?scope=cutoff`; remove and student withdraw also work on `Cutoff`. A cut off student keeps `advanceEntryOf` (no double registration) but `open-listings` stays available to them. UI: AdvanceListing list view has tabs Advance list / To review / **Cut off** (Move, Move all), overview has a Cut off column. Student `/BookCheckup` shows the Cut off state.
- **Walk-in leaves the advance listing**: `leaveAdvanceForService` removes the student's `Waiting | Pending | Cutoff` advance entry of the same service (status `Removed`, student told) on `POST /api/doctor-visits/walk-in` and when the nurse accepts a session-listing request (`PUT /api/consultation-requests/:id/accept`). An entry that already holds a queue number stays.
- **No show**: an advance entry that held a queue number (`Scheduled`) and whose appointment ended without being seen shows as `No show` (`advanceOutcomeOf`: queue `Void` or attendance `Absent`), `Done` when seen, `Ended` when the place was cancelled. Derived at read time, the stored status stays `Scheduled`.

## Waiting list + session queue (current model, `migration_queue_waiting_list.sql`)
Run `migration_queue_waiting_list.sql` after `migration_specializations_visit_types.sql` (idempotent, `--default-character-set=utf8mb4`). **It supersedes the booking / approval / hybrid-slot bullets in the sections below** (student time-block booking, booking approvals, `auto_confirm`, `by_open_slot` are gone; their columns stay unused).
- **Students do not book a time.** `POST /api/student/consultation-requests` creates a **listing request** (`Waiting for Approval`, no number) for one category (`visit_type`); refused (409) when the nurse closed that service's listing or its listing limit is reached. The category must be covered by a doctor that has an account (`eligibleCategories()`, `GET /api/consultation-requests/categories`), else 409. The student gets a number only when the nurse accepts (`PUT /api/consultation-requests/:id/accept`, nurse only, refused when the limit is reached; the number is `consultation_requests.queue_no`, taken from `queue_counters` by `takeQueueNo`, so numbers follow the order of acceptance); the live position is `queue_position` / `queue_total` in `REQUEST_SELECT`. One order everywhere: `REQUEST_ORDER` (`is_priority DESC, queue_no ASC`).
- Request statuses: `Waiting for Approval -> Waiting List -> (Awaiting Reconfirmation -> Reconfirmed, optional) -> Appointed -> Fulfilled | Missed`; `Denied` (nurse/doctor decline or remove with a reason, `PUT /:id/deny`, works from `Waiting for Approval` too), `Withdrawn` (student, also while pending). `Booked` exists only for old rows. `REQUEST_VISIBLE_STATUSES` includes `Waiting for Approval`; `ACTIVE_REQUEST_STATUSES` (accepted, waiting) does not, so pending rows have no position and are not counted. A student cannot have a second open request (any of the active statuses or `Appointed`) in the same category.
- **Listing control per consultation service** (`migration_consultation_services.sql`, run after `migration_consultations_offered.sql`; the backend also creates the table on first use, `ensureServiceListingTable`): `consultation_service_listing (visit_type, listing_open, listing_limit)`; `listingOf()` returns open?, limit, `accepted` (statuses in `ACTIVE_STATUS_SQL`), `pending`, `listing_full`. The **doctors** open/close a service and set the number of listings in My Profile > "Check-up listings" (`components/scheduling/ServiceListing.jsx`, only the services the doctor covers; `PUT /api/consultations-offered/:visitType/listing` with `sender_id`, doctor only, others get 403; empty limit = no limit; `POST /api/consultations-offered` ignores listing fields). The **nurse only views** it (status chip + "x accepted of y" in the Check-up Services card of Manage Doctor Accounts, which has no listing controls). `GET /api/consultation-requests/categories` and `GET /api/consultations-offered` carry `accepted / pending / listing_open / listing_limit / listing_full` (+ `can_request`); the student's request form and `/BookCheckup` show "x of y accepted" per service. Waiting list tab "To accept" holds the pending requests (nurse: Accept / Decline; doctor: view).
- **Appointing = a place in a session queue, no time slot.** `POST /api/doctor-schedules/:id/appoint` (`student_id, date, request_id`) and "Appoint next" `POST /api/doctor-schedules/:id/auto-appoint` (`date, count | request_ids, visit_type`; takes the front of the category in `REQUEST_ORDER`) create a `doctor_appointments` row spanning the session window with `queue_lane='Listed'`, `queue_no` (next number of that schedule + day, `nextQueueNo`) and `queue_state='Waiting'`. Capacity = `queueCapacity(schedule)` (slot grid x patients per slot; the form calls them "minutes per patient" / "patients at once"). `assertQueueFits` replaces the time-slot checks; `assertAppointmentFits` / `/slots` stay for direct appointments, follow-ups, referrals and batches. Queue rows are excluded from the doctor's timed-overlap count (`queue_state IS NULL`) and cannot be rescheduled one by one (cancel + appoint again). The doctor reschedules the **whole upcoming one-date session** with `PUT /api/doctor-schedules/:id/reschedule` (`schedule_date, start_time, end_time, reason`, doctor of the schedule only, before it starts; the queue rows move with it keeping their numbers, students and parents are told; rescheduling lives inside the session's **Edit** button (`ScheduleFormModal.jsx`: for an upcoming one-date session with students queued the date/hours stay editable and ask for a reason, the form calls `PUT /api/doctor-schedules/:id/reschedule` first, then the normal PUT); there is **no separate Reschedule button** on the session card and `RescheduleSessionModal` was removed; refused when timed appointments, a clash, an unavailable day or a too-small capacity). `PUT /api/doctor-schedules/:id` still refuses timing changes while students are in the queue.
- **Queue lanes and states.** `Listed` (#1, #2 ...) is served first; `Walk-in` (W1, W2 ...) has its own numbering and is called only when no listed student waits. `queue_state`: `Waiting | Serving | Done | Void`. Doctor-only endpoints: `PUT /api/doctor-schedules/:id/queue/call-next` (refuses while the serving number is undocumented), `PUT /api/doctor-visits/:appointment_id/queue/skip` (number becomes `Void`, stays in the list, request -> `Missed`, student told). `PUT /api/doctor-visits/:appointment_id/queue/accommodate` (nurse or doctor, session running + `allow_walk_in`) creates a walk-in lane row (`parent_appointment_id` = the void row) and puts the request back to `Appointed`. `POST /api/doctor-visits/walk-in` also joins the walk-in lane of the running session. Snapshot: `GET /api/doctor-schedules/:id/queue?date=` (`buildQueueSnapshot`, `peopleAhead`). Documenting a consultation calls `finishQueueEntry` (queue `Done`, request `Fulfilled`); deleting the assessment calls `reopenQueueEntry`.
- Cron (5 min): `closeFinishedQueues` - numbers never called when the session ended are cancelled and the request returns to the waiting list keeping its place (`returnRequestToWaitingList`), the student is told; then `markExpiredAppointmentsAbsent`.

- **Predictive demand weekday shape**: `backend/src/utils/medicineForecast.js` measures the seasonal index from the 30-day history (`measureSeasonality`) as the plain textbook ratio: index = mean demand of that weekday / average daily demand (ADD, open days only); no shrinkage, no renormalizing, no date-level variation (all removed on purpose, the thesis formula is used as is). Predicted demand = ADD x index, so for the first forecast day it equals that weekday's own mean (Wed 5, 5, 7, 8 -> 6.25). Sunday = 0; a weekday with no sample or no demand = flat 1. Later days shift the window (phase 2), so ADD drifts a little. The `seasonality` option still forces fixed weights (rescaled by `normalizeWeights`). **Weeks 2+ (k > 7)**: the weekday index is a weighted average (`measureWeeklySeasonality`, `weightedWeekWeights`): half the plain 30-day index, half the per-history-week indices (4 blocks of 7 days; the analog block counts 0.4, others 0.2 each, analog rotates oldest -> newest per forecast week), then `distinctWeekWeights` (+ a dry-run repair with `simulateWeek`) gives every forecast week a peak, mid peak and lowest weekday that differ from the earlier weeks (min rank gap `RANK_GAP`, min spread `MIN_SPREAD`), so each forecast week has its own high/low shape. Week 1 (k 1-7) stays the plain formula and matches Medicine Dispensed Overview. A custom `seasonality` option stays fixed for all weeks.
